# 공정 운영

## 접수 (0단계)

받은 것을 먼저 분류한다. **무엇이 있느냐로 공정이 달라진다.**

| 받은 것 | 공정 |
|---|---|
| 제품 사진만 | 전체 공정 (1~7) |
| 제품 사진 + 레퍼런스 영상 | 2단계(레퍼런스 분해) 포함 |
| 대본만 | 3단계 검수부터 → 4·5·6·7 |
| 레퍼런스 영상만 | 2단계 → 제품을 정한 뒤 1단계로 되돌아감 |
| "소재 떨어졌다" | 6단계만 (소재 담당) |

**질문은 세 개까지.** 제품명·가격·카테고리 중 빠진 것만 묻는다.
그 이상 물으면 채널 주인이 대신 기획하게 된다. 나머지는 가정하고 `확인 필요` 로 남긴다.

## 작업지시서

각 담당을 부를 때 이 다섯 줄을 준다. 없으면 담당이 추측으로 일한다.

```
제품:      (이름 · 가격 · 카테고리)
받은 자료: (사진 N장 / 특징 / 레퍼런스)
이번 각:   (한 문장 — 누구의 어떤 짜증을 몇 초에)
쓸 것:     (앞 단계 산출물 경로. 예: 03_script.md 의 대본)
주의:      (확인 필요 항목 · 이 편에서 피할 것)
```

양식은 `../templates/work-order.md`. 지시서는 `00_work-order.md` 에 저장하고 **모든 담당이 같은 것을 본다.**

## 병렬과 직렬

**병렬로 돌려도 되는 것** (서로 입력이 필요 없다)
- 1단계 리서치 ∥ 분석(모드 A)
- 6단계 소재는 3단계 대본이 끝난 뒤 아무 때나 (5단계와 병렬 가능)

**반드시 직렬인 것** (앞의 산출물이 입력이다)
- 분석(모드 B) → 대본 : 20초 비트 초안이 대본의 골격
- 대본 → 제목 : 제목은 대본에서만 나온다
- 제목 → 마케팅 : 썸네일 문구는 제목 앞줄에서 나온다

순서를 어기면 정합이 깨지고, 정합은 7단계에서 잡히지 않고 **다시 3단계로 돌아가야 한다.**

## 게이트 통과 기록

통과시킬 때마다 `07_qa.md` 에 한 줄 남긴다. 근거 없이 통과시킨 게이트는 통과가 아니다.

```
[3 대본] 통과 — 공백 제외 97자 / 9줄 / 규칙6 확인 / brief.yaml 파싱 OK
[4 제목] 반려 1회 → 통과 — #2,#4 가 같은 유형이어서 반려, 판단 궁금으로 교체됨
```

## 반려 절차

1. **무엇을** — 어느 항목인지 (제목 #2, 대본 6번째 줄)
2. **왜** — 어느 규칙을 어겼는지 (같은 궁금증 유형 / 20자 초과 / 답이 대본에 없음)
3. **어떻게** — 방향만. 문장을 써주지 않는다 ("판단 궁금 갈래에서 다시")

한 번에 세 개까지. 같은 담당 2회 반려면 **지시서를 고쳐서** 세 번째를 보낸다.

## 재작업이 앞 단계로 번질 때

| 발견된 문제 | 어디까지 되돌리나 |
|---|---|
| 제목이 대본과 안 맞음 | 제목만 (4단계) |
| 대본 마지막에 CTA 없음 | 대본 (3단계), 제목은 그대로 |
| 대본의 각이 후킹 근거와 다름 | 3단계. 분석까지 되돌릴 필요는 없다 |
| 후킹 8개에 근거가 없음 | 1단계 분석. **대본 전에 잡아야 한다** |
| 제품 정보가 틀림 | 0단계. 전부 다시 |

그래서 게이트는 **앞 단계에서 엄하게** 본다. 뒤에서 잡으면 재작업 비용이 몇 배가 된다.

## 한 편 소요 시간 목표

| 단계 | 목표 |
|---|---|
| 0 접수 | 즉시 |
| 1 리서치 ∥ 분석 | 한 번에 |
| 3 대본 | 반려 1회까지 |
| 4 제목 | 반려 1회까지 |
| 5 마케팅 | 반려 0회 (앞이 제대로면 반려가 안 난다) |
| 6 소재 | 한 번에 |
| 7 최종 검수 | 계산 3개 + 정합 4개 |

**5단계에서 반려가 나면 3·4단계 게이트가 헐거웠다는 뜻이다.** 다음 편에서 게이트를 조인다.
